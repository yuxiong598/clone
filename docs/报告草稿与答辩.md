## 一、设计目标及架构

在实验 3 合约之上实现用户应用层，用户在页面中创建订单、授权付款、确认收货、发起争议和仲裁。浏览器读取公开链上数据；交易由用户各自 MetaMask 签名。前端不保管私钥，没有由服务器代替用户签名的业务后端。

调用路径：浏览器界面 → Wagmi/Viem → MetaMask 签名 → POTOS RPC → Escrow / YRHToken 合约。读取路径：合约事件识别订单 id → getOrder(id) 读取当前状态 → 按地址与状态显示操作。

事件是业务发生过的记录，不能仅靠 OrderCreated 事件判断订单当前状态；订单后续可能付款、完成或争议，因此每个订单卡片读取 getOrder。

## 二、合约及状态机

沿用实验 3：Created → Paid → Completed；Paid 可超期退款变为 Refunded；买卖双方可把 Paid 变为 Disputed，仲裁人 resolve 后变为 Completed 或 Refunded。resolve 只允许仲裁人调用，confirm 只允许买家调用。

本次未加入卖家发货状态或多签仲裁，避免与实验 3 已部署合约 ABI 不兼容。时间线通过现有事件实现，无需变更合约。

## 三、必做功能的实现说明

1. 订单列表从 OrderCreated 事件恢复 id，买卖双方从事件得到；每行通过 getOrder 读取链上最新状态。索引总数与 orderCount 对照，辅助发现漏数据。
2. 创建订单验证非零卖家地址、卖家不等于买家、正金额、小数精度、整数期限及非空描述。金额使用 parseUnits，期限使用最新区块时间加分钟数，不用浏览器时间决定合约期限。
3. 单按钮付款先在订单对应 Token 上 approve(Escrow, amount)，等待成功回执后才调用 deposit(id)，分别由用户签名。操作中锁定按钮，防止连续重复提交。
4. 买家且 Paid 显示确认收货；买家或卖家且 Paid 显示争议；仲裁人且 Disputed 显示两个裁决按钮。角色可以重叠，顶部按订单统计显示买家、卖家数量。
5. 网络不匹配提示切链；展示当前账户、仲裁人、余额、错误及交易处理阶段。

## 四、加分项：订单时间线

共享事件索引每次读取不超过十个区块，将 Escrow 的全部业务事件按区块号、日志序号排序，再按订单 id 展示时间线。每条包含事件名称、区块号和交易链接。resolve 事件还显示判给卖家或退给买家。交易失败回滚不会产生已确认业务事件，因此失败交易需另外从钱包记录取证。

扫描从真实部署区块开始，在当前浏览器会话保留检查点并增量同步。短尾部回扫用于处理浅链重组；没有实现面向生产的持久化索引器或深度重组处理。

## 六、课程要求解答与答辩

### 解B-1：为什么必须有两笔交易？为什么要等待授权确认？

ERC20 的 approve 修改买家对 Escrow 的 allowance；deposit 才由 Escrow 调用 transferFrom 把代币转入托管。两个合约的这两次操作是独立的交易，当前 Token 不提供 permit 或同等单签授权能力。即便同一按钮串联，也仍需两次签名和两笔链上交易。

deposit 执行时合约读取的 allowance 必须已经生效，故等待 approve 成功回执后再发第二笔。第一笔成功后关闭页面时，allowance 仍在链上，订单还是 Created，代币仍在买家账户。用户可以继续付款或撤销授权。

### 解B-2：隐藏仲裁按钮是否是安全边界？

前端根据当前连接地址是否等于 arbiter 显示按钮，是用户体验层判断。用户可以改网页或直接调用合约，但 resolve 的 onlyArbiter 会在链上检查 msg.sender，非仲裁人会 revert。真正的资金权限依赖合约，不能依赖网页隐藏按钮。

### 解B-3：路线 B 中 resolve 的 From 是谁？与路线 A 有何不同？

路线 B 是 C 在 MetaMask 中签名，链上交易 From 是 C 的地址，也是合约 arbiter。路线 A 是后端持有仲裁人私钥，收到 HTTP 请求后由服务器签名，From 是服务器钱包地址。两者都必须满足合约 onlyArbiter；区别在于私钥在哪里保管、谁主动授权交易和如何限制业务入口。截图中应以真实交易 From 为证据。

### 解B-4：列表从事件重建，直接用 Remix 创建的订单能看见吗？

能，只要是同一网络、同一合约地址并且扫描起点覆盖创建区块。OrderCreated 由合约发出，和交易从哪个页面、脚本或 Remix 发送无关。前端应用数据是公开链上事件和状态的解释，不是网页私有数据库里的订单。错误网络、错误合约地址或扫描区块缺失则看不到。

### 解B-5：前端没有私钥是否意味着公开代码就能盗币？

不能仅凭公开前端代码盗取用户代币。读取公开代码、公开订单和 ABI 不会获得用户签名能力。写操作仍需账户签名，以及合约权限、状态和 Token allowance 校验。但用户若对恶意页面签署了不当授权，或者钱包本身泄露，仍可能损失资产；所以应核对 MetaMask 中的目标 Token、spender 与金额。

### 为什么后端持私钥风险更高？为什么“订单列表”还要恢复？

后端私钥一旦泄露，攻击者就能直接充当该账户，绕过 HTTP 层控制。如果该账户是仲裁人，就能对允许仲裁的争议订单签名裁决。前端路线各用户自己签名，不必把任何人的私钥交给应用服务器。

区块链提供 mapping 并不自动提供数据库式分页查询；本合约虽然有 orderCount，课程要求用事件恢复列表，利于建立创建记录及交易哈希索引。事件用于发现订单和历史，getOrder 用于读取当前状态。这也说明业务可见性来自链上事实，应用层负责检索和呈现。

### 如果绕开前端，卖家能确认收货吗？仲裁人能裁决未争议订单吗？

卖家 confirm 会被 onlyBuyer 拒绝；仲裁人对 Paid 订单 resolve 会被 inStatus(Disputed) 拒绝。新增自动化测试验证这些约束。失败的上链交易会消耗 gas，但业务状态回滚；如果钱包估算阶段就拒绝发送，则没有链上交易哈希和 gas 消耗。

## 七、局限与改进

本次以课程演示为目标。大量历史区块下十块一批扫描较慢；生产环境可引入持久化事件索引服务、分页、确认数及更完整的重组处理。真实 ERC20 还有手续费代币、不返回 bool、恶意回调等兼容性问题；实验合约以组内 YRHToken 为前提，不能据此认定支持任意 Token。超期退款规则仍以原实验合约的实际逻辑为准。
